Versioning in Git

main holds the approved architecture: the baseline and every approved plateau. A change lives on its branch until the board decides; the board decides on one pinned commit; the decision itself is a commit.

Parallel changes

Several changes can be open on the same Application at once. They can collide at three levels; each level has its own guard, and most of the work is preventing collisions rather than resolving them.

LevelExampleCaught byWhen

1. Detect overlap when the change is opened

When a change is opened, its scope (elements, plateaus, Applications) is compared with every open change; while designing, the comparison uses each branch's actual diff. The change card shows the overlap, and the owner picks one of three answers.

Sequence

B depends on A. B's branch builds on A's preview and cannot enter the merge queue before A is merged.

Recorded as dependsOn on B's work package.

Combine

Both become one change with one work package, one branch and one review.

Recorded as one change file; the other change is closed with a link.

Run in parallel

Both go on. The owner who merges second integrates, and the board can approve with an order condition.

Recorded as a note on both changes; C4 warns until an order is declared.

2. One file per change

  • A change's work package, the blocks it introduces (inside extend abb.<app> { … }) and its relationships live in model/bb/changes/<work package>.c4. Two changes adding blocks never edit the same lines.
  • Plateau membership is made of relationships, never tags: the baseline aggregates what exists; each later plateau is the previous one, plus what its work packages realize, minus what they retire. New, changed and retired are derived.
  • Editing an existing block (description, owner, metadata) still happens in its own file. A conflict there is a real one, and a person resolves it.
  • When the plateau is promoted, the bot folds the change files into the model and deletes them.

3. Merge one at a time, and keep approvals honest

Each merge goes through the merge queue (GitLab merge train or GitHub merge queue): arch-validate runs on the branch plus the latest main, so the second change is checked against the first.

The board approved WP-REQ-05's own diff at commit 5d2e8f1. After main is taken in, the toolbox compares that diff with the new one:

  • ✓Same diff, checks greenThe approval stands and arb-decision stays green. No new review.
  • !Updated since reviewThe resolution changed blocks in the reviewed scope. The chair chooses a review of the delta only, or a full review.
  • ✕Back to DesignThe result contradicts the target: it uses a block the other change retires (P5) or changes a retired one (C2).

The owner of the change that merges second resolves conflicts. Agents may propose the resolution as a commit; a person accepts it. Only the bot writes ARB records, so nobody resolves a conflict in one.
