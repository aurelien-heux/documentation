Catalog: user journey and implementation architecture

How skills, tools and MCP servers move from an author to the assistant and Sweep, and the services that carry them. Based on the Catalog rules in aitoolbox-component-rules.md and the bounded contexts of the domain reference.

Draft · 2026-11-13 · the backend context name is provisional (CTX-LIB) until the Catalog naming clash with CTX-CAT is settled.

1. User journey

Four people touch the Catalog: the author who publishes a skill, the reviewer who checks it for everyone, the user who adds it to their assistant, and the admin who opens it to Sweep and retires it.

Author: publish a skill

  1. Write name, one line, instructions, tools it may use, one example request. Or point to a Git repository with SKILL.md and skill.json; tags become versions.
  2. Test runs the automatic checks and one try in the assistant. Write tools run in dry-run mode during this try.
  3. Submit: Just me or My team goes live at once; Everyone goes to review.
  4. Follows the review in the skill's Discussion; fixes and resubmits if asked.

User: find and use

  1. Opens Catalog from the rail, or Browse catalog from the assistant's Tools menu.
  2. Reads the item page: what it does, the lock line if it can change something, Try asking.
  3. Adds it. It appears in the Tools menu at once, under Built-in, Organisation or Yours.
  4. Asks a question. The assistant loads the skill when the request matches, and stops on an approval card before any action that changes something.

Reviewer and admin

  1. Reviewer opens Core › Catalog › Review, reads instructions and tools, tries it, ticks the three points, then publishes or asks for changes.
  2. Admin sets the ceiling for actions that change something, separately for the assistant and Sweep.
  3. Admin binds items to Sweep phases (implement, review, test, release).
  4. Retiring names a successor; installs move after 30 days.

2. Version lifecycle

Each version has one stage. The stage is what the Mine tab shows and what the backend enforces.

3. Implementation architecture

One new backend context owns the Catalog. Runtime calls never go straight from the model to a tool: every call passes one gateway that applies the ceiling, raises the approval card and injects credentials.

Publish path

  1. Stepper saves a draft through the Registry API (Postgres row, files as JSON).
  2. Test starts the Checks runner: JSON Schema of skill.json, gitleaks, every tool exists in the registry, risk worked out.
  3. Dry-run try: the assistant runs with the draft on; the gateway answers write calls with a preview, never the real action.
  4. Submit moves the stage; Everyone creates a review task.
  5. On publish, the workflow writes the bundle to skill-bundles/<item>/<sha256>/ and emits EVT-CATALOG-ITEM-PUBLISHED.

Run path (assistant)

  1. At conversation start, the assistant asks the Resolver for the user's installed items (one cached call).
  2. The system prompt gets only name and one line per skill.
  3. When a request matches, the model calls load_skill and gets the full SKILL.md.
  4. Tool calls go to the gateway: it checks the item's risk against the user setting and the admin ceiling, raises the approval card if needed, adds the credential and calls the tool.

Run path (Sweep)

  1. CTX-ORC asks the Resolver for items bound to the Run's phase.
  2. Skills go into the Context pack; tools become Capabilities of the Run.
  3. Calls use the same gateway with the Sweep ceiling; an approval emits EVT-APPROVAL-REQUESTED and pauses the Run.
  4. The Trace records the skill version used, so a Run can be replayed.

5. Choices behind the design

  • Postgres plus immutable bundles, the same split as the architecture knowledge base (DEC-KB-07): workflow changes in seconds, published content never changes, and a Sweep Run can name the exact version it used.
  • Risk is worked out from the tools, never declared by the author. That makes "review again only if it adds a write tool" a set comparison.
  • Skills load on demand. Only names and one-liners sit in the prompt, so fifty installed skills cost little.
  • One gateway for the assistant and Sweep keeps one approval card, one ceiling and one audit log. Credentials stay in CTX-INT (INV-07).
  • MCP servers stay platform-owned in v1. The "add by https URL" option in Assistant settings should go, or become a request to the platform team.

Open before build: the context name (Catalog vs CTX-CAT), "tool" vs Capability in the ubiquitous language, and whether team skills with write tools need review.
