Skill publication processthe same for a new skill and a new version
1
Write
In the app, or from a Git repository (SKILL.md and skill.json; versions follow tags). A draft is usable by its author only.
2
Test
Automatic checks: the manifest, no secrets in the text, every tool exists, and whether it changes something (worked out from its tools). Then one try in the assistant with the skill on. Both are required to continue.
3
Submit
Pick who can use it: just you, your team (live at once; the team is responsible), or everyone (goes to review).
4
Review
For everyone only. A champion or a platform admin tries it, ticks three points, talks with the author in the skill’s discussion, then publishes or asks for changes. Target: 2 working days.
5
Published
In the Catalog and the assistant’s Tools menu; admins can turn it on for Sweep phases. A new version goes through Test again, and back to Review only if it adds an action that changes something. Retiring a skill names its successor and gives users 30 days.
What is in the Catalog
  • MCPDevOpsPipelines, builds, deployments, pull requests
  • MCPKnowledge baseDocs, runbooks, architecture model, ARB decisions
  • TLDeploy environment · Reserve environmentFrom Environments; they change something, so they ask first
  • TLCreate Jira ticketWith the run or the conversation as context
  • SKSkillsPublished by people: migrations, runbooks, reviews, release notes
Minimal by default. No tags on cards. The item page has one action (Add to my assistant) and says in one line when the item can change something. Reviewed, usage and source sit in one line of metadata. Filters are a kind switch and a search.
